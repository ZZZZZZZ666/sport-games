# Regina Sports：技术方案与可行性评估

用 Regina 设备当体感手柄，做一套 11 项运动小游戏的合集（玩法类似 Wii Sports Resort）。

## 0. 已确认的决定（2026-10-17）

| 事项 | 决定 |
|---|---|
| 游戏引擎 | **Godot 4**（理由见第 2 节“为什么选 Godot”） |
| 震动反馈 | 暂时不做；以后改硬件时再加（DRV2605L 方案），固件和协议先预留接口 |
| 拇指摔跤 | 去掉 |
| 设备数量 | 目前只有 1 个，以后会增加。连接部分按多设备设计，加设备不用改架构 |
| 手机当手柄 | **支持**。手机扫码打开网页就能当手柄用，可以和 Regina 混着用，凑齐 2–4 人（见第 2 节“手机当手柄”） |
| 美术方向 | 现代风格化卡通，模型精细度中等偏上（见第 2 节“美术方向”） |
| 手柄屏幕 | 充分利用 OLED，显示游戏状态和当前按键功能（见第 3 节“手柄屏幕用法”） |

## 1. 现有硬件盘点

信息来自 Regina 原项目的源码和 README。

| 部件 | 型号 / 情况 | 对本项目的意义 |
|---|---|---|
| 主控 | ESP32-C6，支持 BLE 5.0（不支持经典蓝牙） | 够用；可以做多设备连接，运算力足够在设备上跑姿态融合 |
| IMU | BMI270 六轴，量程 ±8 g / ±2000 °/s，**没有磁力计** | 俯仰和横滚可以用重力校正，**朝向角（yaw）会慢慢漂移** |
| 按键 | A / B / C / D 四个 | 扳机键、确认键、功能键需要分配到这四个键上 |
| 旋钮 | 两个 16 档编码器（一大一小） | 可以当方向选择、菜单滚动的输入 |
| 屏幕 | 1.3 寸 OLED，SH1106 驱动，128×64 单色 | 显示玩家编号、电量、游戏状态、按键功能提示（见第 3 节） |
| 电源 | AXP202 + 400 mAh 电池，已有电量百分比和充电状态接口 | 低电量提示可以直接做 |
| 声音 | 蜂鸣器 | 震动反馈不能用时，可以先用声音代替 |
| **震动马达** | **没有** | 震动反馈**需要改硬件** |
| 摇杆 / 压力传感器 | **没有** | 拇指摔跤已去掉，其他游戏不需要 |

现有固件的情况：每 50 ms 轮询一次（不到 20 Hz），BLE 发送 float32、不带时间戳，所有设备名都是同一个 `Reginaaaa:)`。这些都**不满足**挥动检测的要求，需要专门写一版手柄固件（见第 3 节）。

## 2. 推荐技术栈

```
┌──────────────┐  BLE 5 (100 Hz 打包)                 ┌──────────────────┐
│ Regina 手柄 ×N │ ◀──────────────────────────────▶  │                  │   UDP localhost   ┌──────────────────┐
└──────────────┘  屏幕内容 / 玩家编号 / 归零 / 蜂鸣器   │  regina-hub (PC)  │ ─────────────────▶ │  Godot 4 游戏      │
┌──────────────┐  Wi-Fi：HTTPS 网页 + WebSocket       │  Python           │ ◀───────────────── │  GDScript          │
│  手机 ×N       │ ◀──────────────────────────────▶  │  bleak + aiohttp  │  统一的手柄数据     └──────────────────┘
└──────────────┘  屏幕内容 / 震动（安卓）              │                  │
┌──────────────┐                                     │                  │
│ 模拟手柄       │ ──────────────────────────────▶  │                  │
└──────────────┘  键盘鼠标 / 录制回放                  └──────────────────┘
```

连接程序（hub）把三种来源都整理成**同一种手柄数据格式**交给游戏，游戏完全不关心某个玩家用的是 Regina、手机还是模拟手柄。

| 层 | 选型 | 理由 |
|---|---|---|
| 手柄固件 | **ESP-IDF 5.x + C++**，蓝牙协议栈改用 **NimBLE** | 和原项目同一套工具链，可以复用按键、旋钮、屏幕、电源、IMU 这几部分硬件驱动；NimBLE 比 Bluedroid 更省内存、更轻 |
| 姿态融合 | **在 hub 里跑** Mahony 六轴融合，用设备时间戳积分 | （P0 实现时调整）手柄只上传带设备时间戳的原始数据，这样 Regina 和手机共用同一套算法、手感一致，调参也不用重新烧录固件；因为积分用的是设备时间戳，BLE 延迟抖动不影响精度 |
| PC 连接桥 | **Python 3.11+ + bleak + aiohttp**（bleak 在 Windows 上底层走 WinRT） | 原项目已经在用 bleak；aiohttp 负责给手机提供手柄网页和 WebSocket。它统一负责扫描、配对、断线重连、分配玩家编号和录制数据，游戏本身不用碰蓝牙和网络 |
| 游戏引擎 | **Godot 4.x 最新稳定版（4.4 起自带 Jolt 物理）+ GDScript** | 免费、体积小，自带 3D、物理、动画和场景编辑器，能导出 Windows exe；11 个小游戏的场景用编辑器做，比写纯代码引擎快得多 |
| 桥接到游戏的协议 | 本机 UDP，用小端二进制包 | 延迟最低，GDScript 里用 `PacketPeerUDP` 加 `PackedByteArray.decode_*` 就能解析 |
| 开发工具 | 桥接程序自带**模拟手柄**（用鼠标或键盘模拟姿态）和**录制回放**功能 | 没有设备也能开发；挥拍识别的阈值可以拿录好的真实数据反复调试 |

### 为什么选 Godot：性能、资源占用和画面

| 维度 | Godot 4（原生程序） | 网页（Three.js 跑在 Chrome 里） |
|---|---|---|
| 渲染后端 | Vulkan / D3D12，原生调用 GPU | WebGL2，或者 WebGPU（Three.js 的 WebGPU 渲染器），中间多一层浏览器转译 |
| CPU | 渲染、物理（Jolt）、动画都是 C++ 原生代码；GDScript 只负责轻量的游戏逻辑 | 引擎、物理、逻辑全都跑在 JS 主线程上，物理只能靠 Rapier 的 WASM 版本 |
| 内存 | 小型 3D 游戏大约 150–300 MB | 浏览器本身就要占几百 MB，再加上游戏本身 |
| 画面工具 | 内置 SSAO、SSR、辉光、体积雾、AgX 色调映射、烘焙光照（LightmapGI）、自动 LOD、遮挡剔除、粒子系统、可视化的着色器和材质编辑 | 后处理、阴影、LOD 都要自己挑选第三方库再组合 |
| 场景制作 | 有可视化编辑器，直接导入 glTF 格式的模型 | 只能写代码摆放场景 |
| 发布 | 导出成 Windows exe（约 80–100 MB） | 打开网页就能玩 |

在“充分利用 GPU、CPU 和内存”这个目标上，原生的 Godot 明显占优。网页方案唯一的长处是不用装程序。

### 手机当手柄

**可行。**手机自带陀螺仪和加速度计（多数还有磁力计），屏幕能做虚拟按键，安卓还能震动，在某些方面比 Regina 更强。

| 项 | 做法 |
|---|---|
| 怎么连接 | 手机和电脑连同一个 Wi-Fi。游戏画面上显示二维码，手机扫码后打开 hub 提供的手柄网页，通过 WebSocket 实时发送数据。不用装 App |
| 传感器 | 网页读取 `devicemotion` 事件里的角速度和加速度，在手机上跑和 Regina 一样的 Mahony 融合，两种手柄的手感保持一致 |
| 按键 | 屏幕上画 A/B/C/D 和扳机区域；可以按游戏需要切换布局，比如水上摩托显示油门滑条 |
| 屏幕 | 显示和 OLED 一样的游戏信息，但可以是彩色、更大 |
| 震动 | 安卓 Chrome 支持 `navigator.vibrate`，**手机玩家现在就有震动**；iOS Safari 不支持网页震动 |
| 玩家编号 | 和 Regina 统一由 hub 分配，可以混着用，比如 P1 用 Regina，P2–P4 用手机 |

需要注意的限制：

- **必须用 HTTPS**：iOS 和安卓都要求在 HTTPS 页面里才能读取运动传感器。hub 会用自签名证书，所以每台手机第一次打开时要手动点一次“继续访问”；iOS 还要点一下“允许访问运动与方向”。
- **采样率较低**：浏览器里的传感器频率一般在 60 Hz 左右，比 Regina 的 200 Hz 低。挥拍识别够用，但击球时机的精度会差一些。以后如果需要更高频率，或者想让 iOS 也能震动，可以再做一个原生 App。
- **Wi-Fi 延迟有抖动**：一般 5–30 ms，取决于路由器。
- **安全**：挥拍时手机容易脱手，建议加手机挂绳，或者在游戏开始前提示玩家握紧。

### 美术方向：现代风格化卡通

目标是参考 Nintendo Switch Sports 那种观感：比例圆润、造型干净、材质柔和、光照通透。比纯低多边形精细，但不追求写实。

| 方面 | 做法 |
|---|---|
| 模型 | 中等面数，边缘平滑、带圆角。角色每个约 1.5–3 万面，主要道具约 0.5–1 万面，场景物件按需要使用 LOD |
| 着色 | 自写风格化着色器：柔和的 2–3 级明暗过渡 + 边缘光（rim light），可选描边；材质保留 PBR 的粗糙度和金属度，让球拍、水面、金属这些材质有层次 |
| 光照与后期 | AgX 色调映射、SSAO、辉光、体积雾；户外场景用烘焙光照或 SDFGI；回放镜头加景深 |
| 特效 | 击球拖尾、命中粒子、水花；水面用 Gerstner 波加泡沫；草地用 GPU 实例化并带风动 |
| 角色 | 统一的人形骨骼，动画用 Godot 自带的人形重定向；可以做一个简单的头像和服装编辑器，让每个玩家有自己的角色 |
| 素材来源 | 用 Quaternius、KayKit 等 CC0 素材作为底子；动画素材需另行确认许可（允许在成品游戏中使用，不必然允许公开原始动画文件）；道具可以先用 AI 3D 生成工具出初稿，再在 Blender 里修整；最后都用同一套着色器统一风格 |
| 性能预算 | 目标是 1080p、60 fps，在中端独显上运行（RTX 3050 / GTX 1660 这一档，需要实测确认）。画面里可见的面数控制在 50 万以内，绘制调用（draw call）控制在 1000 以内，贴图用 1K–2K 并开启显存压缩 |
| 低配选项 | 设置里可以切换到 Mobile 渲染器，关掉 SSAO 和体积雾，给核显电脑用 |

省资源的通用做法：

- 静态场景用 LightmapGI 烘焙光照，运行时几乎不用算光照；
- 大量重复的物体（观众、树、浮标）用 MultiMesh 一次批量绘制；
- 开启自动 LOD 和遮挡剔除；
- 物理固定 120 Hz，用 Jolt。

### 考虑过但没选的方案

- **网页方案（TypeScript + Three.js + Rapier + Web Bluetooth）**：不用装桥接程序，开发迭代快，只有一个设备时配对也不麻烦。但在 GPU、CPU、内存效率和画面工具上都不如原生 Godot（见上表），而且 3D 场景只能纯代码搭建。
- **Unity**：在 Windows 上用 BLE 必须装第三方插件，项目也偏重，没必要。
- **把手势识别放在设备上**：每调一次阈值就要重新烧录固件，迭代太慢。设备只负责“传感器到姿态”这一步，具体游戏怎么理解动作放在 Godot 里做。

## 3. 手柄固件要做的事

> P0 实现时做了调整：姿态融合、零偏校准和归零都移到了 hub（理由见第 2 节）。固件只负责 200 Hz 带时间戳采样、按键旋钮、电量、OLED 和蜂鸣器。实际协议以 [protocol.md](protocol.md) 为准，下面第 2–4 条描述的功能现在由 hub 实现。


1. **采样**：把 BMI270 的加速度和陀螺仪都设成 200 Hz 输出，用 INT1（GPIO23）的数据就绪中断或芯片内部 FIFO 来读，每个样本带微秒时间戳。
2. **自动零偏校准**：开机时静止 1 秒做一次初始校准；运行中一旦检测到静止（陀螺仪幅值和加速度模长的方差都很小，并持续约 0.5 秒），就用低通滤波慢慢更新陀螺仪零偏。
3. **姿态融合**：用六轴 Mahony 算出四元数。俯仰和横滚靠重力持续校正；yaw 只能保证相对准确。
4. **一键归零**：长按某个键（比如 D 键 1 秒），把当前朝向记为“正前方”，作为新的参考姿态。游戏也可以通过下行指令触发归零。
5. **BLE 上行**（每 40 ms 发一次 notify，一次打包 4 个样本，MTU 协商到 247）：
   - 每个样本包含：时间戳增量（u16）、四元数（4 个 int16）、陀螺仪（3 个 int16）、去掉重力后的线加速度（3 个 int16），共约 22 字节
   - 按键和旋钮状态单独一个特征值，只在变化时发送，保证低延迟
   - 电量、充电状态、固件版本：每 10 秒发一次，或者有变化时发送
   - 数据量：每个手柄约 2.2 KB/s，4 个手柄约 9 KB/s，BLE 完全扛得住
6. **BLE 下行**：设置玩家编号（OLED 上大字显示 P1–P4）、蜂鸣器提示音、震动波形（预留，等硬件改版后启用）、触发归零。
7. **连接管理**：断开后立刻重新广播；设备名带上 MAC 地址后 4 位（比如 `Regina-3F2A`），方便区分多个手柄；屏幕上显示电量低于 15% 的提示。

### 手柄屏幕用法（OLED，128×64 单色）

**做法**：电脑不推送整屏像素，而是发送“界面描述”指令，比如“标题 + 力度条 75% + 按键提示 A=拉弓 B=取消”，每条只有几十字节，由固件用 M5GFX 画出来。少数需要图案的地方（图标、简单动画帧），偶尔推送一张 1 KB 的位图。这样 BLE 带宽几乎不受影响，屏幕刷新也流畅。

**通用显示内容**（所有游戏都有）：

- 顶部状态栏：玩家编号（P1–P4）、电量、连接状态
- 底部按键提示：当前 A/B/C/D 分别是什么功能。按键少，所以这一项特别有用
- 系统提示：“请保持静止，正在校准”、归零成功的动画、“轮到你了”、低电量警告

**各游戏的专属显示**：

| 游戏 | OLED 显示 |
|---|---|
| 射箭 | 拉弓力度条、风向箭头和风速 |
| 高尔夫 | 当前球杆、上一杆的力度条、杆数 |
| 保龄球 | 第几格、本局分数；出球后显示击倒的瓶数 |
| 篮球 | 剩余时间、得分、连中次数 |
| 乒乓球 / 网球 | 比分；击球后短暂显示球速和旋转类型（上旋、下旋、侧旋） |
| 排球 | 下一个动作提示（发球、接球、扣球） |
| 拳击 | 自己和对手的体力条 |
| 螺旋桨飞机 | 高度、速度、剩余气球数 |
| 水上摩托 | 速度、油门、圈数 |
| 滑板 | 当前连招和得分 |

手机手柄显示同样的内容，用彩色界面，屏幕更大。

## 4. 手柄功能可行性

| 需求 | 能否实现 | 说明 |
|---|---|---|
| 姿态追踪 | ✅ | 俯仰和横滚是绝对准确的；yaw 每分钟会漂几度，所以必须配合一键归零 |
| 挥动动作检测 | ✅ | 需要把采样提到 200 Hz（目前只有 20 Hz） |
| 自动零偏校准 | ✅ | 靠静止检测加在线更新零偏实现 |
| 扳机键 / 确认键 / 方向 / 功能键 | ⚠️ 键不够多 | 建议分配：A = 扳机，B = 确认，C = 返回或菜单，D = 功能或长按归零，大旋钮 = 方向和数值，小旋钮 = 辅助。具体好不好按，要看实际握持时手指能碰到哪些键 |
| 无线连接 / 低电量 / 断线重连 | ✅ | 桥接程序记住每个手柄的 MAC 地址，掉线后自动重连；AXP202 已经能读电量 |
| 震动反馈 | ⏸ 暂不做，后续改硬件 | 推荐加一颗 **DRV2605L 触觉驱动芯片 + 一个线性马达或扁平震动马达**。芯片挂在现有 I²C 总线（GPIO10/11）上，不占用额外 GPIO，还内置 100 多种震动波形。另外要看外壳里有没有空间放。改硬件之前，先用“蜂鸣器提示音 + 屏幕画面抖动”代替 |
| 玩家编号与配对（2–4 人） | ✅ | Regina 和手机可以混着用，hub 统一分配 P1–P4；人数不够时，回合制游戏（高尔夫、保龄球、射箭、篮球）可以轮流传同一个手柄。Windows 同时连 4 个 BLE 设备没问题，建议用 BLE 5 的蓝牙适配器（比如 Intel AX200/AX210），一些廉价的 CSR 蓝牙棒连多个设备时不稳定。注意：**拳击双手版每人要两个手柄**，先做单手柄版 |
| 一键姿态归零 | ✅ | 见第 3 节第 4 条 |
| 延迟 | ✅ | BLE 连接间隔 15–30 ms，加上打包发送，总延迟大约 30–50 ms，体感游戏可以接受 |
| 续航 | ✅ | 估算功耗约 40–60 mA，400 mAh 电池大约能用 6–8 小时（需要实测） |

## 5. 11 个游戏的可行性

总体思路：**不去算手柄的空间位置**（加速度二次积分不可行，前面已经分析过），而是用“姿态 + 角速度 + 线加速度峰值 + 按键时机”来识别动作，和 Wii 的做法一样。每个游戏用一个状态机加阈值规则来实现，先不上机器学习。

| 游戏 | 识别方法 | 难度 | 风险 |
|---|---|---|---|
| 螺旋桨飞机 | 俯仰和横滚直接映射到飞机的俯仰和滚转；扳机键加速 | ★ | 无 |
| 滑板 | 横滚控制转向，快速往上抬控制跳跃（ollie） | ★ | 无 |
| 射箭 | 用相对 yaw 和俯仰瞄准；按住 A 拉弓（按住越久力度越大），松开放箭 | ★★ | yaw 漂移，每局开始自动归零 |
| 保龄球 | 按住 B 挥臂，松开的瞬间就是出球时机；用挥臂时的角速度峰值算球速，出手时的横滚角算弧线旋转 | ★★ | 无 |
| 篮球 | 按住 B 举手，往上甩出时松开；出手角度用俯仰角，力度用角速度峰值 | ★★ | 无 |
| 乒乓球 | 挥拍方向用主要角速度轴的正负号判断；挥拍速度用角速度峰值；旋转类型（上旋、下旋、侧旋）根据击球瞬间拍面的俯仰或横滚变化来判断 | ★★★ | 旋转只能分大类，精确的转速做不出来 |
| 网球 | 正手和反手根据挥拍时 yaw 角速度的方向判断；力量用角速度峰值；击球时机看挥拍峰值的时刻和球到达时间差多少 | ★★★ | 要预测球的到达时间，需要容错窗口 |
| 高尔夫 | 识别“静止瞄准 → 后摆 → 下挥 → 送杆”四个阶段；力度看后摆的幅度和下挥的峰值；方向看击球瞬间的横滚角（杆面开合） | ★★★ | 用力挥杆时角速度可能超过 ±2000 °/s 的量程，要处理读数被截断的情况 |
| 排球 | 发球是“往上抛加过头挥臂”，接球是“手平举后往上抬”，扣球是“过头快速往下挥”；按当前回合需要哪种动作，结合姿态和角速度方向来区分 | ★★★ | 三种动作容易混淆，需要用游戏上下文限定当前可能的动作 |
| 水上摩托 | 一个手柄横着用两只手握（像车把），横滚控制转向，扳机键或大旋钮控制油门 | ★★ | 无；如果要两个手柄组合成一个车把，同样能做 |
| 拳击 | **单手柄版**：手柄握在出拳的手里，出拳靠前向线加速度峰值，再按姿态区分直拳和勾拳；按住 B 防守；对手是电脑。以后有两个手柄时，再改成双手各一个 | ★★★ | 单手柄只能一只手出拳，打击感会差一些 |

## 6. 开发阶段建议

1. **P0 基础**：手柄固件（含 OLED 界面指令）→ hub（Regina 配对和重连、手机手柄网页、玩家编号、模拟手柄、录制回放）→ Godot 里的手柄调试场景（显示 3D 姿态、各项曲线、按键状态）+ 风格化着色器和光照的基础模板
2. **P1 只靠倾斜控制的游戏**：螺旋桨飞机、滑板、射箭、保龄球
3. **P2 挥拍类游戏**：乒乓球、网球、高尔夫、篮球
4. **P3 复杂动作游戏**：排球、拳击、水上摩托
5. **硬件改版**（以后再做）：加震动芯片和马达
